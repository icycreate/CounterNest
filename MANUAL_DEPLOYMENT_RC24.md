# RC24 manual installation and deployment

2026-10-25. The source is untested, unbuilt and undeployed. These are instructions for an authorized operator; none were executed in this task.

1. Preserve the current source, environment configuration and a full database/storage backup. RC24 builds on RC23. Do not reset the database or replay already-applied migrations. Do not automatically backfill customer links.
2. Review `supabase/migrations/202610251000_customer_recognition.sql`. Apply it manually in a separately authorized staging environment after the prior migration chain. It is transactional and includes exact-definition guards for acceptance and scheduled editing. If a guard rejects an installation with locally modified functions, stop and reconcile those definitions; do not remove the guards blindly.
3. The migration creates private recognition metadata/association/retry tables and RPCs, a full-phone index, and permits nullable customer_id on scheduled orders. No historical association is inserted. Keep RLS enabled and do not grant public candidate search or direct write access to the private tables. The customer-service gate remains admin/cashier; manager order permissions are not expanded.
4. No new package, API provider, secret, SMS account, Storage bucket or Vercel variable is needed. Keep existing Supabase URL/public anon key configuration. Never place service-role keys or WhatsApp/Web Push private credentials in frontend environment variables.
5. When separately authorized, validate in staging: exact international matches with formatting differences, different country codes, name conflicts, multiple records, archived restore permissions, unparseable historical phones, optional duplicate-checked creation, cross-workspace denial, anonymous denial, revision conflicts, retry idempotency, guest acceptance/editing, post-acceptance linking, completed-sale customer history and existing loyalty exactly once. Confirm public tracking never exposes association data. No such checks were performed here.
6. Use the normal reviewed GitHub/Vercel workflow only when authorized. The package includes existing Vite/deployment configuration; usual build command is npm run build and output directory is dist. No build was run here. Exclude credentials and generated dependencies. Update installed PWAs through the usual release/reopen flow; the cache identifier is RC24.
7. After deployment, authorized staff open Catalogue Requests or the accepted order and select Review Match. Review the original submission and candidate records. Confirm identity directly with the customer, choose a record and enter a reason, or Leave as Guest. Creation is optional and warns on possible duplicates. Archived records require explicit admin restore before linking. Use the existing Customer List history to view linked requests, scheduled/custom orders, completed sales and loyalty activity.

## Backup and rollback
Add catalogue_customer_links and customer_link_operations to your full database backup coverage; the phone-rule table is reproducible from the migration. Existing portable workspace backup allowlists do not automatically include the new tables. No backup, restore or purge procedure was run or validated here. Do not use old portable exports as the sole backup of these associations.

Do not roll back the frontend to a release that silently chooses a Customer List entry for nullable guest scheduled orders. Prefer a forward correction while retaining association/audit data. Do not restore NOT NULL on customer_id while guest orders exist. Do not delete the new relationship tables or customer records as a rollback shortcut.

## Limitations
Phone matching is not phone ownership verification. The bundled phone metadata may be old; regionless/non-geographic numbers may need manual review. There is no OTP integration. Paid/historical sales remain unchanged and cannot be relinked through this feature. Real migration compatibility, RLS, UI behavior, concurrency and loyalty must be validated later before release.
